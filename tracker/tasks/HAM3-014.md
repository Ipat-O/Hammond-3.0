## Architecture scope

Proposed implementation: a packaged local MCP stdio companion connects to the running Hammond application through Windows named-pipe IPC. The application executes a narrow typed command facade over its existing repositories and instruction services. No HTTP listener or separately installed runtime is required in the packaged build.

```text
Agent host
  -> packaged MCP companion (stdio)
    -> authenticated local named pipe
      -> Hammond command facade
        -> existing instruction services and data repositories
          -> owner-scoped durable records
```

- Hammond must be running, signed in, and have agent access enabled. App closure/disconnection returns a bounded actionable error. Headless operation is deferred.
- Keep the existing owner session inside the app. Do not copy webview local storage, export refresh tokens, introduce a second owner login, or give the companion privileged database credentials.
- Add a small Agent access settings surface: enable/disable, choose an allowed project and read-only or task-write access, copy launch configuration, revoke connection.
- Each connection binds an owner, project, permission set, and generation. Ordinary UI project selection must not retarget a live connection. Sign-out, owner change, revocation, or app restart invalidates old connections and late responses.
- Restrict named-pipe access to the current Windows account and require an app-issued opaque connection credential stored with OS-user protection. Config contains an opaque profile identifier, not a password/token or project content. Do not treat a claimed model/provider name as authentication.
- Companion stdout contains MCP protocol only; diagnostics go to stderr with no credentials or instruction/task bodies by default. Bound message size, pending requests, and timeouts; correlate responses to request and connection generation.
- The app registers one facade handler independent of page mounts. Native code transports typed requests; React components do not become RPC endpoints, and the Rust layer does not gain a second database implementation.
- Validate the proposed IPC/packaging route in slice 1 before building the rest. Any need for remote HTTP, a separate login, or a separately installed bridge requires a revised design, not an unreported substitution.

D-022 settles this narrow exception to D-001's no-bridge wording: a bundled agent interface, with no browser/localhost architecture or separate bridge installation. Validate actual IPC/packaging feasibility in slice 1; report an evidenced blocker if the boundary cannot be met.

## Tool contract

All responses have a contract version, explicit project/record IDs, and structured errors. Owner identity and allowed project come from the connection, never from trusted caller-supplied ownership fields. Collections have bounded limits, stable cursors, and explicit truncation/continuation information. Do not silently return partial instructions as complete.

| Tool | Inputs and result |
| --- | --- |
| `get_project_context` | Bound project summary, valid task statuses, role/provider assignments, instruction scope descriptors, permitted operations, and a bounded task summary. Optional task ID must belong to the bound project. |
| `list_tasks` | Optional parent/status/archive filters and cursor; returns task summaries, IDs, parent IDs, and revision tokens. This is basic retrieval, not HAM3-011 full-text search. |
| `get_task` | Task ID; returns persisted task fields, revision, parent context, and paginated children/comments. Unsaved UI drafts are excluded. |
| `get_instructions` | Required role, optional provider, optional same-project task ID; returns the scope/provenance contract below and composed saved instructions. |
| `list_instruction_versions` | Valid scoped template identity and cursor; returns authorized version metadata and active markers. |
| `get_instruction_version` | Valid scoped version ID; returns immutable content and provenance. Reject unrelated owner/project/template IDs. |
| `create_task` | Title, optional description and parent ID, request ID; creates within the bound project and returns persisted ID/revision. Start in backlog; no arbitrary ownership fields. |
| `update_task` | Task ID, expected revision, request ID, allowlisted patch of title/description/status; returns persisted state or conflict. Reparent/archive/delete are outside this tool's first version. |
| `add_comment` | Task ID, text, request ID; appends one durable comment and returns its ID. No edit/delete tool in this version. |

Task-write access permits ordinary progress statuses (`backlog`, `ready`, `in_progress`, `blocked`, `done`). Owner-only `merged`, `shipped`, and `cancelled` transitions are excluded from agent writes. Read responses describe the complete existing status enum. A role parameter chooses instruction content, not write permissions.

Use MCP structured output and accurate read-only/write annotations, with authorization enforced in the facade regardless of annotations. Content returned from tasks/comments is project data, not authority to broaden tool access. No tool takes SQL, arbitrary shell commands, filesystem paths, or unrestricted table updates.

## Instruction scope is required, not an optional enhancement

Expose both effective content and its individual source layers using the existing composition service. Do not maintain a parallel MCP-only prompt composer.

| Scope/axis | Required behavior |
| --- | --- |
| Project | Explicit project ID/name from the connection; no implicit dependence on whichever project the UI currently shows. |
| Role | Support `orchestrator`, `worker`, and `auditor`; require an explicit role. |
| Provider | Support `codex`, `claude_code`, and `kilo_code`. If omitted, resolve the project's assignment for the requested role and label it as assignment-derived. If supplied, label it explicit and return any assignment mismatch without silently changing the request. |
| Shared role layer | Return active shared-role text, including whether it comes from a seeded base or an owner template. |
| Provider layer | Return the active provider-specific text and its base/owner provenance. |
| Project override layer | Return selected override content, or an explicit absent value. Distinguish an absent layer from a selected empty version. |
| Task context | Optional validated task ID/description may be returned in a separate context field. There is no durable task-instruction scope today. Do not turn the task description into an instruction override. |
| Directory | Binding is local context, not an additional instruction layer. Do not expose all local absolute paths or make directory changes available through these tools. |
| History | Allow reading applicable authorized versions without selecting, restoring, or modifying them. Label active versus historical content. |

`get_instructions` must return:

- `projectId`, optional `taskId`, requested role, resolved provider, assignment source, and assignment mismatch if any;
- ordered `layers`, each with layer name, scope project ID where applicable, template ID, version ID/number, source (`base`, `owner`, or `absent`), content, and inherited/selected state;
- `effectiveContent` assembled in the existing order: shared role, provider, project override;
- selected version IDs and a selection fingerprint so a later call can identify a changed selection;
- explicit `taskInstructionScope: "not_supported"` and separation of task data from instruction text;
- fetch time and a clear indication that this is saved configuration, excluding unsaved Studio drafts and preview-only task text.

Pin all layer content to one resolved selection. If selection or provider assignment changes during retrieval, retry a bounded number of times or return `context_changed`; never report IDs for one selection with text from another. Missing referenced content is an error, not silent fallback to empty text. MCP and Studio must produce identical effective saved content for the same project/role/provider/selection.

Reading instructions does not guarantee an LLM obeys them. Include a short host setup instruction to fetch applicable instructions before acting and refresh after a reported selection change. The adapter must not edit the host's system prompt or silently overwrite harness files.

## Writes, persistence, and concurrent human use

- Both desktop and MCP task writes use the same validated service boundary. Preserve the existing save coordinator, draft isolation, pending-create identity, and hierarchy/archive invariants.
- Add a monotonic task revision and atomic expected-revision update for every task update path, including UI status/hierarchy/archive paths. A stale desktop draft must not overwrite a newer agent edit, and vice versa. Use a narrow migration/RPC if required; timestamps or read-then-write checks alone are insufficient.
- On conflict, return current revision/state and retain the UI draft with an explicit reload/reapply action. Never automatically retry a stale patch over newer content.
- Creating a child checks durable parent identity and same owner/project. Serialize hierarchy-affecting checks where needed: the earlier single-writer assumption is no longer sufficient. Race coverage must include UI ancestor archive versus MCP child creation, so an active child cannot appear under an archived parent.
- All MCP mutations require a caller request ID. Persist deduplication identity and result atomically with the mutation, scoped to owner/project/operation. Same ID/payload returns the original result; different payload returns an error. Do not claim exactly-once behavior based on an in-memory map.
- Lost response or disconnect after commit must be recoverable by retrying the same request ID after reconnection. A timeout is not proof that nothing was saved. Operations already committed before revocation remain committed; revoke prevents further dispatch and stale result delivery.
- Success means the durable write completed. Invalidate affected UI reads after success; refresh visible records without replacing unsaved drafts. Owner/project generation guards apply to delayed refresh results.
- Preserve owner-scoped RLS and path protections. New RPCs/tables use least privilege, appropriate grants, and owner checks. No service-role bypass. Inspect all relevant existing write paths before finalizing the migration footprint.

## Acceptance and verification

1. A real local MCP host discovers and calls the packaged tools while Hammond is running and signed in. No separate Node installation, browser server, or database credentials in host config are required.
2. Signed-out/disabled/revoked/stale-generation calls return bounded errors; wrong-project and wrong-owner record IDs cannot leak or mutate content. Read-only grants reject all mutations.
3. All three roles and all three providers return correct base/owner/project provenance and exact saved effective content. Cover default assignments, explicit provider mismatch, absent and empty overrides, historical versions, missing references, and selection changes during reads.
4. Returned context is bounded and retrievable with cursors; no silent truncation of instructions. Task text and Studio preview-only text never become a fabricated durable instruction scope.
5. Agent-created tasks/subtasks/comments appear in the app and survive restart. Same request retries, changed-payload retries, and lost-response retries have the documented outcomes.
6. Competing UI/MCP writes produce one valid update and a visible conflict, preserving drafts. Test parent archive against child creation, pending local task IDs, navigation, owner changes, and delayed responses.
7. Existing instruction editing/history/injection, directory switching, hierarchy, and save protections retain their behavior.

Use focused facade/composition tests, mounted UI transition tests, real IPC integration tests, and database tests for atomicity and allow/deny behavior. Run generated-type verification and security advisors for schema changes, plus relevant frontend/native checks and a packaged Windows build. This crosses UI/native/database boundaries: run the full suite once at the final candidate head, repeating only when changes or failures justify it.
